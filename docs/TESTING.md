# Testing

How the suite runs, what each file guards, how to change a value a test holds, and what only a person can check. The release gates that wrap the suite are in [Operations](OPERATIONS.md#release-gates); the commands are in the [README](../README.md#work-locally). Scene terms such as reveal, film, dwell, stand-in and text guard are defined in the [Glossary](GLOSSARY.md).

## Running tests

`npm test` runs `node --test "test/*.test.mjs"`: Node's own test runner, no framework. The quotes let Node expand the glob, so the command is the same in every shell. Each file runs in its own process, and `test/support/` lies outside the glob.

| Run                 | Command                                                                      |
| ------------------- | ---------------------------------------------------------------------------- |
| Everything          | `npm test`                                                                   |
| One file            | `node --test test/scene-loader.test.mjs`                                     |
| Tests by name       | `node --test --test-name-pattern="reveal's mark" test/scene-loader.test.mjs` |
| Every file, by name | `node --test --test-name-pattern="loading line" "test/*.test.mjs"`           |

Options go before the files. `npm test -- --test-name-pattern=…` appends the option after the glob, where Node does not apply it, and every test runs.

Tests that build or bundle write under `.tmp-preview-review/` (ignored by Git), each in a folder of its own that it removes afterwards. bundle-output's real build also leaves its output manifest in `.cache/build-outputs/` (ignored by Git).

[test/support/](../test/support/) holds shared helpers. The self-contained [landmark-baseline.json](../test/support/landmark-baseline.json) fixture records original byte patches and hashes for the four bounded landmark repairs; it needs neither private artwork nor Python in CI.

| `code.mjs`        | `source(path)`, `flat(code)`                                   | Reads a repository file; flattens JavaScript                                                                                                                                      |
| `css.mjs`         | `flat(css)`, `rule()`, `rules()`, `mediaBlock()`, `contrast()` | Flattens CSS; finds a selector's first standalone rule, every matching rule, every block of a media query; WCAG contrast of two `#rrggbb` colours                                 |

There are three `flat()`s, one per language; each makes a check read the same however Prettier wraps the source. All collapse whitespace runs to one space and drop the space just inside brackets and parentheses. `code.mjs` also drops `//` comment lines and trailing commas; `html.mjs` also drops spaces beside `<` and `>`. Use the one for the language you check.

## Test styles

1. **Source checks.** A test reads a source file and asserts on its text, flattened with `flat()` so formatting cannot break it: scene-bootstrap (index.js wiring), markup-accessibility (HTML and CSS), hosting and workflows, and parts of others. They pin how parts are wired where running them would need a browser.
2. **Sandboxed browser scripts.** The UI modules and quality.js are IIFEs; tests run them in a `node:vm` context with a fake `window` and `document` and controllable timers, observers, frames and `fetch`: boot, contact, scene-loader, scene-quality, scene-basics and startup-cost, among others.
3. **Scene modules on headless Three.js.** Tests import `src/scene/*.js` as ES modules. Three.js's math, geometry and materials run in Node; rendering.js takes its renderer from an injected `createRenderer`, so tests pass a fake and no WebGL context exists. Delivered models are read with `glb.mjs`.
4. **Real builds and scripts.** bundle-output builds the site with `node build.mjs --dist --outdir` into `.tmp-preview-review/bundle-output-*` and checks the payload; it also runs two fixture builds there, a `--check` build that must refuse a first-party module in the shared chunk and a `--dist` build whose tower model changes. build runs fixture builds, the watcher, the dev-port check and [tools/owned-process.mjs](../tools/owned-process.mjs) `spawnOwned()`, which `npm run dev` and `npm run watch` use to start their children: each child gets its own process group (outside Windows) and stopping it stops only that group, never a process found by name or port. terrain-build and lantern bundle their chunks with esbuild to find the shader anchors after compaction. smoke-pages runs the smoke script in Bash.

## Timing-sensitive tests

Four tests time real work with `performance.now()`, so a heavily loaded machine can fail them; the suite runs files in parallel.

| Test                                                                                                   | Asserts                                                                                                      |
| ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| terrain-build: `the film terrain builds in idle slices and arrives only where it cannot show mid-shot` | Every slice under 50 ms (`no long task (… ms)`)                                                              |
| hill-silhouette: `the ranges build in short idle slices and fade in wherever they could show mid-shot` | Every slice under 50 ms (`no long task (… ms)`), the median under 8 ms (`median slice … ms`)                 |
| hill-silhouette: `under the reveal's fade the ranges rush in back-to-back slices of at most 12 ms`     | The longest under 50 ms (`longest rushed slice … ms`), the median at most 13 ms (`median rushed slice … ms`) |
| mountain-massifs: `the composed build lands in short slices and frees itself when cancelled`           | Every slice under 50 ms (`no long task (… ms)`), the median under 8 ms (`median slice … ms`)                 |

When one fails, rerun its file alone. A failure that repeats on an idle machine is a regression ([Troubleshooting](TROUBLESHOOTING.md#a-slice-timing-test-fails-on-a-busy-machine)).

## Locked values

Many tests hold exact values: copy, budgets, sizes, constants, CSS declarations, workflow lines, shot names and dwells, baked tables. When a change to one is intended:

1. Change the source and the test's expected value in the same commit, and say in the message what changed and why the old value no longer holds.
2. Update every doc that states the value ([AGENTS.md](../AGENTS.md) rule 5), for example the model sizes in [Assets](ASSETS.md#models) or a shot's dwell in [Scene modes](SCENE-MODES.md#shots).
3. Where a test holds two files equal, change both. Each restated value below exists so a module or shader can use it without importing its source (helpers.js runs without imports, the lazy chunks import only `three`, and shaders take numbers as text); a comment beside it names its source.
4. Regenerate baked tables instead of editing them: `node tools/bake-root-shade.mjs` prints `ROOT_RESTS`, `ROOT_SHADE` and `ROOT_COVER` to paste into terrain-build.js, and the terrain test compares them with a fresh bake of both tree models; `node tools/bake-opening-outline.mjs` rewrites src/scene/opening-outline.js, and the opening-star test compares it with both tower models measured for every variant of The watch.
5. Treat budgets as decisions: reduce the payload first; move a budget only with its reason, in the test and in the docs that state it.

## What the tests do not cover

- **Browsers and GPUs.** No test runs a browser engine, real layout or a WebGL context; shaders are checked as text, never compiled by a driver.
- **Visual output.** No test compares pixels. Framing tests measure geometry, not renders.
- **The share card's picture.** hosting holds `public/og.png`'s format, dimensions, opacity and size, not what it shows.
- **Live hosting.** Headers and Cloudflare settings as served are checked by the deploy's smoke checks and the weekly Cloudflare audit ([Operations](OPERATIONS.md#cloudflare-audit)), not by `npm test`.
- **The live scene's performance.** CI's Lighthouse audits the static title card on runners without a GPU.

## Visual review

A visual change needs a person's review: [Style](STYLE.md#guardrails) lists what to recheck (desktop and portrait frames, motion extremes, reduced motion).

1. Serve the site (`npm run dev` or `npm run preview`) and open the capture URL from the [capture recipe](SCENE-MODES.md#capture-recipe), for example `?quality=high&view=tower&angle=1&tour=0&sceneDebug=1`.
2. Pause for a still frame, in one of two ways:
   - **After the recipe holds.** Load without a preference, wait until every condition in the capture recipe holds, then call `BabelSite.scene.setVisitorPaused(true)`. The frame has every asset, the rocks included, but scene time stands where the pause found it; for a frame that repeats, drive the frame clock as the recipe says.
   - **From the reveal.** Set `window.BabelSite = { scene: { visitorPausedPreference: true } }` before the page's scripts run (for example from a browser automation's init script). The scene keeps its first revealed frame, and each later model, map, shader warm-up, range or terrain change draws one still frame. Scene time advances only on animated frames, so these frames do not depend on how long loading took. The rocks do not reliably arrive this way: they advance only inside a drawn frame (rock-build.js `take()` queues their programs on one frame and commits them on a later one), and finishing their build does not request a frame. Whether they commit depends on how many still frames follow, so `sceneDebug.rocks.status` can stay `loading` and the recipe's rock condition may never hold. Record `sceneDebug.rocks.status` with each capture, and compare two such captures only when it matches.
3. Capture. Paused after the recipe holds, the frame is ready; paused from the reveal, wait until every condition in the capture recipe except the rocks' holds first.
4. Capture a second, text-off frame: set `visibility: hidden` on `#hero-minimal` and `.site-footer`. Do not use `display: none`, which collapses the boxes the scene measures for framing and the text guard and changes the frame. Measure the contrast of the text against the text-off frame under its box, to [Style](STYLE.md#motion-and-accessibility)'s ratios.
5. Compare captures of the same URL and viewport before and after the change only after a 5×5 median filter on both: it removes the scene's fixed grain (a 1280×720 noise grid from the final vignette-grain pass; [Glossary](GLOSSARY.md)) and the smallest stars (2 device px, [starfield.js](../src/scene/starfield.js) `STAR_MIN_FOOTPRINT`), so the difference shows the change.
6. When the accepted look changes, regenerate the share card ([Style](STYLE.md#static-images)); its procedure is in the comment at the top of [tools/og-card.html](../tools/og-card.html).

## Lighthouse

CI's `audit` job runs Lighthouse on the built `dist/` artifact three times and asserts the medians in [lighthouserc.json](../lighthouserc.json):

| Assertion                | Threshold |
| ------------------------ | --------- |
| Performance              | ≥ 0.80    |
| Accessibility            | 1.00      |
| Best practices           | ≥ 0.95    |
| SEO                      | 1.00      |
| Largest contentful paint | ≤ 2500 ms |
| Cumulative layout shift  | ≤ 0.10    |
| Total blocking time      | ≤ 200 ms  |

The runners have no GPU, so this audits the title card. There is no Lighthouse command in `package.json`; for each release, run three default Lighthouse passes of the live scene on GPU hardware and hold the median to the same performance and total-blocking-time gates ([Operations](OPERATIONS.md#release-gates)).
